# Edge 在线语音跨项目对照：关键外部证据

## 已核对来源

1. `edge-tts-rust` v0.1.3（当前《璇玑录》依赖）声明其面向 Microsoft Edge Read Aloud TTS，并提供音色读取、WebSocket 合成、连接池与实时测试能力。
   - https://crates.io/crates/edge-tts-rust

2. 《璇玑录》使用依赖的公开上游 `protocol.rs` 显示：
   - `TrustedClientToken` 是库内固定的 Edge 客户端常量；
   - `ConnectionId` 每请求由 UUID 生成；
   - `muid` 每请求由随机字节生成；
   - `Sec-MS-GEC` 以当前 Unix 时间（转换为 Windows ticks 并按 5 分钟取整）和固定客户端常量计算 SHA-256。
   因而 `Sec-MS-GEC` 不是固定值，也不与某一台电脑绑定。
   - https://raw.githubusercontent.com/initsnow/edge-tts-rust/master/src/protocol.rs
   - https://raw.githubusercontent.com/initsnow/edge-tts-rust/master/src/constants.rs

3. `edge-tts` 生态曾出现旧客户端因缺失动态 `Sec-MS-GEC` 而得到 403 的案例，说明动态握手对于当前服务是必要条件。
   - https://github.com/rany2/edge-tts/issues/290

## 与《牌箓》报告的对照结论

《牌箓》报告确认其旧版 Node 客户端缺少动态 `Sec-MS-GEC`，升级后的客户端具备动态令牌和更新请求特征后可完成 WSS 握手。这一根因适用于“旧客户端握手被拒”。

《璇玑录》从 v260827A 起使用的 `edge-tts-rust` v0.1.3 已实现动态 `Sec-MS-GEC`、随机 `ConnectionId` 和随机 `muid`，并使用 Chromium 143 请求特征。因此，《璇玑录》用户报告的 v260827C URL 中出现 `Sec-MS-GEC` 与 `Sec-MS-GEC-Version=1-143.0.3650.75` 本身证明它不是《牌箓》所述“仅固定 TrustedClientToken、无动态 GEC 的旧握手”问题。

两项目共同点是：均依赖同一 Microsoft Edge Read Aloud 在线服务；音色目录为 HTTPS，合成为 WSS；设置页在进入时自动请求目录会使网络错误立刻可见。两项目的首轮 UI 改进方向也相同：目录刷新失败不得阻断已保存音色或首次设置，应显示非阻断状态并允许主动刷新。

《璇玑录》v260828A 已将语音请求改为三次独立新连接、关闭连接池预热和复用、增加超时并脱敏错误 URL 查询参数。若安装 v260828A 后仍存在 10054，则更值得排查新电脑的网络／代理／安全软件／系统时间，以及 Microsoft 对特定网络出口或请求特征的兼容性，而不是认定为“固定 token 被占用”。
