# 给《牌箓》开发助手：训练场功能设计说明

> **用途**：本说明可直接作为《牌箓》新增“训练场”功能的产品与技术任务书。  
> **设计来源**：借鉴《璇玑录》训练场的成熟经验，但已将“星骰”逻辑抽象为适合牌类学习的通用训练框架。  
> **核心目标**：训练场不是“再做一次占问”，而是让用户先独立练习解牌，再获得结构化反馈、评分与长期复盘。

## 一、为什么《牌箓》应该有训练场

牌类工具最有价值的能力不应只是在用户提问后即时给出牌义，而应帮助用户逐渐形成自己的观察、联想、结构组织与表达能力。普通占问解决的是“这一次如何理解”；训练场解决的是“我是否正在学会理解”。

训练场应被设计为一个有明确起点、过程和反馈的学习闭环：软件先本地确定练习牌面与题目，用户在**看不到 AI 标准答案**的前提下写出自己的解读，随后 AI 以导师身份提供参考、指出亮点与可改进处，并给出百分制评分。用户可以把每次练习保存到历史，长期观察自己在不同主题、牌阵与难度上的进步。

> 训练场的重点不是让 AI 替用户解牌，而是让用户先解，再由 AI 协助复盘。

## 二、建议的训练场核心流程

建议将训练流程固定为以下六步，以形成清晰的学习节奏。

| 步骤 | 用户所见与操作 | 系统职责 |
|---:|---|---|
| 1 | 选择训练范围、难度或牌阵类型；也可以直接点击“开始一题” | 读取本地偏好；默认不限制题材。 |
| 2 | 软件展示一道生活化练习题与已抽出的牌面 | 在本地完成真实随机抽牌；AI 不参与决定牌面。 |
| 3 | 用户查看牌名、正逆位、牌阵位置和必要的基础资料 | 提供练习所需事实，但不提前展示标准解读。 |
| 4 | 用户填写“我的解读” | 保存草稿状态；可设置最小字数提示，但不要强制长篇。 |
| 5 | 用户点击“提交我的解读” | 将题目、真实牌面、牌阵位置与用户文字发送给文字 AI。 |
| 6 | 展示 AI 点评、逐牌参考、亮点、改进建议、总评和 1–100 分；用户可保存到历史 | 将完整练习记录和评分保存到本地档案，供筛选、导出与复盘。 |

对于初期版本，建议优先支持两种题型：**单牌情境题**和**三张牌小牌阵题**。单牌适合初学者建立关键词与情境联系；三张牌可用于练习时间线、关系结构或“现状—阻碍—建议”一类位置关系。不要在第一版就引入过多复杂牌阵，否则会稀释训练反馈质量。

## 三、最重要的技术原则：牌由本地随机源决定，AI 不负责抽牌

这是从《璇玑录》训练场得出的最重要经验之一。不要在提示词中要求 AI“随机抽几张牌”，也不要让模型在 JSON 中返回它声称随机的牌名。语言模型不是可验证的随机源；同一提示词可能得到相近结果，服务端采样、缓存或温度设置也会影响输出。

正确的数据流应当是：

```text
用户点击“开始训练”
        ↓
本地随机模块从牌库抽取牌面、正逆位与牌阵位置
        ↓
软件锁定本次练习的实际牌面
        ↓
把“已确定牌面 + 已确定位置 + 训练范围”发送给 AI
        ↓
AI 只生成相配的练习问题，不能增加、替换或改写牌面
        ↓
用户作答后，AI 只负责参考解读与评分
```

如果《牌箓》采用 Tauri/Rust，可使用操作系统随机熵源，例如 Rust 的 `getrandom` 或等价安全随机接口；若是纯网页环境，应使用 `crypto.getRandomValues()`，而非 `Math.random()`。抽多张牌时必须**不放回抽取**，同一牌阵内不得出现同一张牌两次；正逆位应由独立本地随机位决定。不同训练轮次之间允许自然重复，不需要为了“看起来更随机”而强行避重。

## 四、训练范围与难度的交互设计

训练题材不应默认偏向某一个领域，例如职场或恋爱。建议在设置页增加可复选的“训练出题范围”：默认全部不选，意味着 AI 不收到范围限制；只有用户勾选后，已选范围才会写入出题提示词。这样既保留随机练习的开放性，也满足用户阶段性专项训练的需求。

建议的预设范围如下，并保留一个限 15 字以内的“其它”自定义范围：

| 编号 | 推荐范围 |
|---:|---|
| 1 | 恋爱与亲密关系 |
| 2 | 友情与人际相处 |
| 3 | 家庭与居住生活 |
| 4 | 职场与职业发展 |
| 5 | 学业与能力成长 |
| 6 | 金钱与消费规划 |
| 7 | 身心状态与生活习惯 |
| 8 | 兴趣创作与自我表达 |
| 9 | 出行、旅行与环境变化 |
| 10 | 个人选择与人生方向 |

难度建议采用循序渐进的三档，而不是只用“简单／困难”标签：

| 难度 | 牌面与题目设计 | AI 评分重点 |
|---|---|---|
| 入门 | 单张牌、明确具体的生活情境 | 是否能说出核心象征，并与问题产生基本联系。 |
| 进阶 | 三张牌、固定位置含义 | 是否能处理牌间关系、位置差异与整体叙事。 |
| 综合 | 多张牌或用户指定练习方向 | 是否能建立结构、处理张力与给出不绝对化的建议。 |

初期可以先实现“入门”和“进阶”，将“综合”保留为后续扩展。

## 五、AI 提示词设计

AI 提示词必须区分两个阶段：**出题阶段**与**点评阶段**。出题阶段不应让 AI 返回牌面；点评阶段不应让 AI 随意修改用户已经看见的牌面或牌阵位置。

### 1. 出题阶段的 system 提示词模板

以下是可直接改造的模板。实际牌名、正逆位、位置、范围和难度由程序动态填入。

```text
你是《牌箓》训练场的出题导师。软件已经通过本地随机源确定本次练习的牌面、正逆位与牌阵位置；这些事实不可由你生成、替换、增删或改写。

请根据给定的实际牌面，为学习者生成一道贴近日常生活的牌类解读练习题。题目应具体、开放、没有唯一命运结论，适合用户练习把牌义与情境联系起来。

{如果用户选择了训练范围：本题只能从以下已选范围中选择：……。}
{如果用户选择了难度：本题难度为……。}

只输出合法 JSON：
{"question":"15-60字的中文练习问题"}

不要输出牌名、牌义、标准答案、分析过程或任何其它文字。
```

对应的 user 内容例如：

```text
本地已确定的实际练习信息：
牌阵类型：三张牌（现状—阻碍—建议）
第 1 张：权杖二，正位，位置为现状。
第 2 张：宝剑八，逆位，位置为阻碍。
第 3 张：星币皇后，正位，位置为建议。
请只生成与这组牌相配的练习问题。
```

### 2. 点评阶段的 system 提示词模板

点评的任务不是宣判用户“对或错”，而是评价其是否观察到牌面核心、是否结合题目、是否处理了位置关系、是否避免绝对化语言。输出必须结构化，便于保存和展示。

```text
你是《牌箓》训练场的温和而严谨的导师。用户将提供练习问题、软件已确定的实际牌面与位置，以及用户自己的解读。

请先尊重用户的表达，再结合实际牌面给出可学习的反馈。不要把牌类解读表述为确定预言，不要替代医疗、法律、财务、投资或心理专业意见。评分应评价解读质量，不评价用户人格。

请只输出一个合法 JSON 对象：
{
  "cardReviews":[
    {
      "position":"现状",
      "card":"权杖二",
      "orientation":"正位",
      "userReading":"概括用户对该牌的理解；未提及则为空字符串",
      "referenceReading":"2-4句参考解读，结合牌面、正逆位、位置与练习问题"
    }
  ],
  "structureReview":"2-4句，评价牌与牌、位置与位置之间的关系；单牌训练可为空字符串",
  "highlights":"1-3句，指出用户做得好的具体部分",
  "improvements":"1-3句，给出可执行的改进方向",
  "overallComment":"2-4句，温和、具体的总评",
  "score":85
}

score 必须是 1 至 100 的整数。100 分只用于牌义理解、情境联系、位置关系与表达结构都准确、平衡、完整的优秀答案；不得仅为鼓励而虚高分数。
```

对应的 user 内容应包含完整事实，例如：

```text
练习问题：……
牌阵类型与位置：……
实际牌面：……
用户的解读：……
```

## 六、建议的数据模型与兼容策略

训练记录应该独立于普通占问记录，以便后续按“占问／训练”分开筛选、统计和导出。字段名称可按《牌箓》已有架构调整，但语义应完整保留。

| 字段 | 类型建议 | 含义 |
|---|---|---|
| `id` / `uid` | UUID / string | 本地记录与跨设备交换的稳定标识。 |
| `created` / `updated` | ISO 时间 | 创建与最近修改时间。 |
| `question` | text | 本次训练问题。 |
| `spread_type` | text | 单牌、三张牌或未来扩展的牌阵类型。 |
| `cards_json` | JSON text | 已确定牌面、正逆位、位置、顺序与必要基础资料。 |
| `user_answer` | text | 用户自己的解读。 |
| `ai_compare_json` | JSON text | AI 的逐牌参考、结构反馈、亮点、改进与总评。 |
| `ai_score` | integer | 1–100 分；旧记录默认 0。 |
| `topic_scope` | text / JSON | 本次训练所用范围，可用于之后筛选。 |
| `difficulty` | text | 入门、进阶、综合。 |
| `review_note` | text | 用户后续复盘、现实验证或补充。 |
| `rating` | integer | 用户自己的满意度或复盘评分，可选。 |

若《牌箓》已有数据库，新增 `ai_score`、`ai_compare_json` 等列时应使用迁移策略：对旧记录提供默认值，而不是强制清空或重建数据。历史列表中若 `ai_score` 为 0 或空，应显示“未评分”，从而保证新旧记录可以共存。

## 七、页面与交互建议

训练场页面建议分为三个连续状态，不要把题目、答案和点评混在同一屏上。

| 页面状态 | 界面重点 | 应避免的设计 |
|---|---|---|
| 出题前 | 题材范围、难度、牌阵选择与“开始一题”按钮 | 不要默认向用户展示 AI 标准答案。 |
| 作答中 | 练习问题、牌面、正逆位、位置、用户输入框、重新出题按钮 | 不要在用户作答前展示完整牌义长文。 |
| 点评后 | 评分、逐牌对照、结构点评、亮点、改进、保存与再练一题 | 不要把 AI 评分单独做成唯一重点；评分应被放在反馈语境中。 |

历史档案中，训练记录标题右侧建议显示 `AI 评分 · xx 分`；旧记录显示“未评分”。用户应能按训练范围、牌阵类型、难度、分数区间或关键字回看练习。若《牌箓》已经有标签系统，可使用系统标签或系统字段标识“训练”，但不应把训练来源这种业务事实交给用户随意编辑或删除。

## 八、隐私、模型和安全边界

如果《牌箓》采用用户自定义 AI Profile，应继承以下原则：文字模型由用户选择；密钥不进入数据库、导出包和普通日志；调试日志默认关闭且需对认证字段脱敏。训练时发往 AI 的内容只应包括本次练习所必需的题目、牌面、位置与用户回答，不应无目的上传整个历史档案。

本地图片、牌面素材和数据库的路径读取也应遵循最小权限原则。前端不应拥有任意文件读取权限；如必须读取本地素材，应由后端验证文件位于允许目录中后再提供受限读取能力。

## 九、推荐的分阶段实施顺序

不要一次实现所有变体。建议按下表落地，以尽快交付可用的训练闭环。

| 阶段 | 范围 | 验收标准 |
|---:|---|---|
| 第一阶段：MVP | 单牌训练、本地随机抽牌、用户作答、AI 结构化点评、评分、保存历史 | 用户能从出题到保存完成一条独立训练记录。 |
| 第二阶段 | 三张牌阵、正逆位、训练题材范围、未评分兼容展示、历史筛选 | 用户可按专题和难度进行连续练习。 |
| 第三阶段 | 学习统计、错题／薄弱主题回看、牌阵扩展、用户复盘、导出 | 用户可以看见长期进步，而非只积累文本。 |

## 十、必须加入的测试

训练场不应只做页面冒烟测试。至少应加入以下自动化或单元测试：

| 测试类型 | 需要验证的内容 |
|---|---|
| 本地抽牌测试 | 所有抽出的牌都来自当前牌库；多张牌阵不重复；正逆位值合法。 |
| AI 出题边界测试 | AI 返回的题目不会覆盖本地已确定的 `cards_json`。 |
| 评分解析测试 | AI 返回的评分只能落在 1–100；缺失或非法评分要安全降级为“未评分”。 |
| 数据库迁移测试 | 旧训练记录可在新增评分字段后正常读取。 |
| 导入导出测试 | 训练牌面、回答、AI 点评和评分可往返保存；导出不含 API 密钥。 |
| 权限测试 | 本地素材或图片读取无法越过允许目录。 |

## 十一、实施时应避免的误区

首先，不要让 AI 自己抽牌。其次，不要为了避免重复而破坏真实随机逻辑；同一张牌在不同训练里再次出现是正常的。第三，不要在用户作答前泄露标准答案。第四，不要只让 AI 返回一段笼统的“你解得不错”；必须要求它给出逐牌参考、亮点、改进和清晰评分依据。第五，不要为了新增评分而破坏旧历史记录。第六，不要把 API 密钥或完整训练历史写入调试日志和导出包。

## 十二、给《牌箓》开发助手的最终执行指令

请在不改变《牌箓》现有核心占问功能的前提下，新增一个独立的“训练场”模块。该模块应以“本地真实随机抽牌 → AI 基于已确定牌面出题 → 用户先作答 → AI 结构化点评与 100 分制评分 → 本地保存和可复盘”为主链路。优先完成单牌与三张牌训练、题材范围、历史评分展示和数据兼容；将复杂学习统计放在后续版本。

实现前请先阅读《牌箓》现有的数据模型、模型 Profile、随机抽牌、档案和导入导出代码，复用已有安全机制；若现有架构与本说明不同，应保留本说明中的产品原则与边界，而不是机械照抄字段或组件名称。完成后请执行前端构建、后端测试、数据库迁移测试和目标 Windows 环境验证，并按项目既有版本与补丁规则交付。

> 成功的训练场，应让用户在每次打开时都更愿意自己先读一遍牌，而不是更依赖 AI 先给出答案。
