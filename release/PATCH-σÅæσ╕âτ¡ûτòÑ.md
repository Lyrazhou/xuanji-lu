# 《璇玑录》补丁发布策略

> 当前完整安装包：`v260825A`
> 日期基准：UTC+8
> 当前策略：逐级升级

## 默认交付原则

`v260825A` 是《璇玑录》的第一个完整 Windows 安装包。除非用户明确要求“输出新的完整安装包”，后续每一次功能改进、缺陷修复、视觉资产替换或模型协议扩展，均默认交付**从当前已发布版本到紧邻下一版本**的最小化补丁。

因此，补丁必须按版本顺序安装。已经处于 `v260825B` 的用户，应使用 `v260825B → v260825C` 补丁；已经处于 `v260825C` 的用户，应使用 `v260825C → v260825D` 补丁。不会再默认生成从首个完整包跨越多版直达目标版本的补丁。

| 规则 | 固定要求 |
|---|---|
| 升级模式 | 默认逐级升级，例如 `A → B → C → D`。 |
| 前置校验 | 每份补丁只接受明确指定的紧邻来源版本；不匹配时停止，不替换文件。 |
| 最小替换 | 仅包含当前版本到下一版本的变更文件、资源和必要数据库迁移。 |
| 用户数据隔离 | 不覆盖、不移动、不删除 SQLite、`images`、`backups` 或 Windows 凭据管理器中的模型密钥。 |
| 数据库迁移 | 如迁移不可避免，先创建东八区时间戳 SQLite 备份；迁移失败时保留原库并回滚程序文件。 |
| 回滚 | 替换失败时恢复本次替换前的程序文件，并清晰显示失败原因。 |
| 可追溯性 | 每个补丁附带来源版本、目标版本、变更文件清单、SHA-256 与更新说明。 |

## 新完整安装包

当用户认为补丁链积累到合适阶段并明确提出要求时，才生成新的完整安装包。新的完整包将包含截至该版本的所有程序和内置资源，用户可以选择通过完整包重新安装，而不必继续安装较早的补丁链。

生成新完整安装包后，后续补丁从该完整包之后的下一个版本开始逐级产生；旧补丁链仍保留其对应的来源与目标校验，不自动混用。

## 版本号规则

版本号固定为 `v + yyMMdd + 序号`，日期使用东八区时间。当天首次发布使用 `A`，依序到 `Z`；超过 26 个发布后使用 `AA`、`AB`……；换日后回到 `A`。例如：

```text
v260825A → v260825B → … → v260825Z → v260825AA
v260826A
```
