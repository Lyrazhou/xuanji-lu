# 通用约定：版本编号与 Windows 升级发布规则

**适用范围：** 本文件用于约束需要发布 Windows 桌面软件安装包、升级补丁或两者兼有的项目。将本文件上传至新项目后，应把下列规则视为该项目的既定发布偏好；除非用户明确修改，否则不得自行更改发布策略。

> **核心原则：** 默认只制作严格相邻版本的逐级升级补丁；只有用户明确要求时，才制作新的完整安装包。

## 1. 版本编号规则

用户可见版本号必须采用：

```text
v + yyMMdd + 字母序号
```

其中日期按 **东八区（UTC+8）** 的实际日期计算，`yyMMdd` 使用两位年份、两位月份和两位日期。字母序号表示该东八区日期内的发布次序。

| 发布次序 | 版本示例 | 说明 |
| --- | --- | --- |
| 当日第 1 次 | `v260825A` | 日期为 2026-08-25，序号从 A 开始。 |
| 当日第 2 次 | `v260825B` | 同日递增。 |
| 当日第 26 次 | `v260825Z` | 单字母序列末位。 |
| 当日第 27 次 | `v260825AA` | 不得重置或改用数字；应继续 AA。 |
| 后续同日版本 | `v260825AB`、`v260825AC`…… | 按 Excel 式字母序列继续。 |
| 次日第 1 次 | `v260826A` | 日期变化后重新从 A 开始。 |

版本号必须同时出现在应用侧栏或关于页、发布说明、补丁文件名、发布清单和最终交付说明中。若软件具有内部安装版本（例如 `0.1.7`），每次对外发布也必须递增内部版本，并在发布清单中清楚对应用户可见版本。

## 2. 默认发布策略：严格逐级补丁

默认策略为：

```text
A → B → C → D → ……
```

每个补丁只允许从**紧邻的上一版本**升级到目标版本。例如 `v260825G → v260825H` 补丁只能接受内部版本为 G 对应内部版本的安装，不能用于更早版本，也不能跨越中间版本。

| 要求 | 强制规则 |
| --- | --- |
| 来源版本校验 | 补丁必须读取并校验已安装软件的内部版本；不匹配时必须中止。 |
| 主程序校验 | 补丁必须确认安装目录与主程序存在；不存在时不得继续覆盖。 |
| 更新顺序 | 用户处于较早版本时，应先安装每一个相邻补丁，直到目标版本。 |
| 备份与回滚 | 补丁写入前必须备份原主程序；写入失败时应尝试恢复。 |
| 数据迁移 | 若补丁涉及数据库、图片或配置迁移，必须额外设计迁移前检查、失败回滚与旧数据兼容。 |
| 补丁内容 | 常规补丁应只携带必要的新主程序或最小必需文件；不得无故捆绑用户数据。 |

## 3. 完整安装包的例外规则

完整 Windows 安装包**不是默认交付物**。只有用户以明确文字提出“生成完整安装包”“重新做完整包”“卸载重装使用完整包”等要求时，才生成新的完整安装包。

完整安装包适用于首次安装、从非常早的版本重装、用户不希望逐级安装多个补丁，或补丁迁移失败后的恢复安装。即使已生成完整包，后续常规迭代仍应恢复为逐级补丁策略，直到用户再次明确要求完整包。

## 4. 文件命名与交付物规范

请将 `{产品名}`、`{来源版本}` 和 `{目标版本}` 替换为项目实际名称与版本号。

| 交付物 | 命名模板 | 必须提供 |
| --- | --- | --- |
| 逐级补丁 | `{产品名}-{来源版本}-to-{目标版本}-Patch.exe` | 补丁程序、SHA-256、更新说明、manifest、补丁脚本源文件。 |
| 补丁 SHA-256 | `{补丁文件名}.sha256` | 以标准 `sha256sum` 格式记录文件名和哈希。 |
| 补丁更新说明 | `更新说明-{产品名}-{来源版本}-to-{目标版本}.md` | 升级前提、变更、数据影响、安装步骤、验证结果。 |
| 补丁发布清单 | `manifest-{目标版本}.json` | 内部版本对应、来源校验、哈希、构建目标、验证结果。 |
| 完整安装包 | `{产品名}-{目标版本}-Full-Setup-x64.exe` | 仅在用户明确要求时提供。 |
| 完整包 SHA-256 | `{完整包文件名}.sha256` | 必须提供。 |
| 完整包说明 | `完整安装包说明-{产品名}-{目标版本}.md` | 首次安装、覆盖安装、数据目录与保留边界。 |

## 5. Windows 补丁的实现要求

补丁安装程序应至少完成以下安全步骤：

1. 读取厂商注册表安装路径；若未找到，再尝试卸载登记中的 `InstallLocation`。
2. 清理注册表读取结果可能附带的前导引号，并验证主程序文件存在。
3. 严格校验当前 `DisplayVersion` 或等价内部版本号是否等于来源版本。
4. 提示用户先完全退出软件；无法备份主程序时中止。
5. 备份旧主程序，写入新主程序，更新安装登记版本；成功后删除临时备份。
6. 若写入失败，尝试恢复备份的旧主程序，并向用户显示明确的失败说明。
7. 若有数据目录迁移，迁移必须在覆盖关键文件前后拥有明确的回滚策略；不得静默删除用户数据库、图片、备份或系统凭据。

## 6. 数据与密钥保护原则

发布和升级流程必须坚持本地优先与最小影响原则。

| 数据类型 | 默认处理原则 |
| --- | --- |
| SQLite 数据库 | 常规补丁不得删除或覆盖；需要结构迁移时必须兼容旧数据并保留回滚路径。 |
| 本地图片与附件 | 常规补丁不得删除；迁移目录时需维护数据库中的绝对路径或改用兼容路径。 |
| 用户备份 | 不得自动删除。 |
| 模型 Profile | 不得因普通升级被删除。 |
| API 密钥与系统凭据 | 不得写入日志、导出包、更新说明、发布清单或安装器；除非用户在软件内明确执行删除操作。 |
| 调试日志 | 默认关闭；如提供开关，必须说明隐私边界，并排除认证头和敏感字段。 |

## 7. 发布前必须完成的验证

在交付任何补丁或完整安装包前，至少执行并记录以下验证：

| 验证项 | 要求 |
| --- | --- |
| 前端构建 | 生产构建必须通过。 |
| 后端测试 | 运行全部 Rust 或后端单元测试；新增核心功能必须添加定向回归测试。 |
| Windows 构建 | 生成目标架构的 Windows x64 主程序与安装器。 |
| 补丁编译 | NSIS 或所用安装器脚本必须成功编译。 |
| 归档检查 | 检查补丁或安装包可读；常规补丁应只含计划内的新版主程序。 |
| 哈希验证 | 生成 SHA-256 后必须再次校验为通过。 |
| 版本一致性 | 应用界面、内部版本、安装器、补丁脚本、更新说明和 manifest 必须一致。 |

交付时应清楚写明：目标版本、适用来源版本、安装前需退出软件、测试结果、SHA-256 已验证，以及数据迁移或隐私边界（如适用）。

## 8. 对执行者的明确指令

1. 一律以本文件为默认规则，不得自行改为“所有补丁均基于最初完整包”的跨版本策略。
2. 仅当用户明确请求时才制作完整安装包；否则按紧邻版本制作最小化补丁。
3. 每次开始新版本前先依据东八区时间计算正确的版本号。
4. 不得跳过来源版本校验，也不得将无法确认来源版本的补丁交付给用户。
5. 如用户要求改变发布策略，应在变更前复述新的策略、影响范围和下一次补丁的适用版本。
