# 《璇玑录》开发历程与核心技术难点回顾

> **项目名称**：《璇玑录》——《星骰工作室》本地版  
> **回顾范围**：v260825A 至 v260826D  
> **最终阶段版本**：v260826D（内部版本 0.1.13）  
> **目标平台**：Windows x64

## 一、项目概览：从网页概念到本地个人观星台

《璇玑录》的开发并非简单地把网页嵌入桌面窗口，而是将原有的“星骰工作室”概念重构为一款可长期使用的本地桌面软件。它需要在同一应用中协调占问流程、AI 模型调用、真实随机掷骰、训练点评、本地图片归档、可搜索档案、模型凭据保护、导入导出与 Windows 交付机制。

最终形成的产品以 **Tauri 2 + React + TypeScript + Rust + SQLite** 为基础：React 负责具备血月星盘气质的交互界面，Rust 负责本地文件、数据库、凭据、图片与系统能力，SQLite 承担可检索的长期档案。这个技术结构使《璇玑录》拥有本地应用的稳定存储与系统能力，也保留了前端界面的迭代效率。

> 开发过程中最核心的转变是：不再把占问结果视作一次性网页输出，而是将问题、骰面、解读、训练、评分、图片和复盘组织为一份能够长期积累的个人档案。

## 三、核心技术难点与解决方案

### 1. 从网页产品转化为真正的本地桌面架构

网页原型可以依赖浏览器存储、在线接口和页面状态，但桌面软件必须回答更严格的问题：数据放在哪里、图片如何管理、密钥如何保存、系统默认查看器如何调用、失败时如何恢复、用户升级后旧资料如何继续可用。

项目最终采用前后端分层。前端负责占问、训练、档案、图库、偏好五个业务页面；后端提供受控命令，统一处理 SQLite、文件系统、Credential Manager、随机源和模型请求。这样既避免了前端直接持有高权限文件能力，也使跨页面的数据行为能够被保存、校验和测试。

| 层级 | 主要职责 | 解决的问题 |
|---|---|---|
| React / TypeScript | 界面、交互、页面状态、展示与确认流程 | 保留网页开发效率，并营造血月星盘主题体验。 |
| Tauri IPC | 前后端命令边界 | 将敏感操作限制为可审计的后端命令。 |
| Rust | 文件、SQLite、凭据、网络请求、系统调用 | 获得 Windows 本地能力与一致的错误处理。 |
| SQLite | 占问、训练、标签、图库索引、偏好 | 让一次性内容成为可查询、可导出、可迁移的档案。 |

### 2. 用户自主管理模型，而不预置服务与密钥

《璇玑录》明确要求不绑定模型厂商、不预置服务和密钥，并允许文字处理与生图使用不同 Profile。这使模型配置不再是一个简单下拉框，而是一套本地安全边界。

系统实现了多 Profile、协议类型、API 地址、模型名称、认证方式、超时、额外请求头与额外参数的结构；文字与图片能力可独立选择。API 密钥不写入 SQLite、导出包、安装包或普通偏好，而是保存到 Windows Credential Manager。调试日志默认关闭，开启后也会对 `token`、`secret`、`authorization`、`api_key` 等字段脱敏。

这一设计解决了两个相互矛盾的目标：一方面让用户可以使用不同服务商、模型和自定义网关；另一方面避免软件因“方便配置”而把密钥泄露到档案、日志或发布物中。

### 3. 兼容不同生图服务的请求与响应差异

生图服务看似都使用“OpenAI Images 兼容接口”，但模型之间对尺寸、质量、输出格式和响应字段的要求并不一致。开发中曾出现 `dall-e-3` 因尺寸非法返回服务端错误，以及不同服务对 `url`、`b64_json`、`b64Json` 或其它 Base64 字段响应不一致的问题。

项目将生图请求从单一固定 payload 改为模型感知的构造逻辑：为 `dall-e-3` 选用合法横版尺寸，为 `gpt-image-*` 避免发送不兼容的 DALL·E 专属参数，并允许用户以 Profile 覆写尺寸、质量、输出格式与响应格式。收到结果后，后端兼容远程 URL 下载与 Base64 解码，使用文件魔数识别 PNG、JPEG、WebP 等格式，再以安全文件名归档。

这项工作使“请求成功”和“结果可用”成为完整链路，而不是只在 API 返回 200 时停止。

### 4. 图片不入数据库：本地归档、命名和关联设计

将图片直接保存为数据库 BLOB 会使数据库膨胀、备份沉重，也不利于用户直接查看图片。因此，《璇玑录》采用“**文件归档 + SQLite 索引**”的结构：图片落在 `data/images` 下，数据库只保存绝对路径、占问关联、生成模式、问题和骰面摘要。

归档文件采用“月份目录 + 时间 + 输出模式 + 问题摘要 + 记录 ID”的命名结构，既可按时间浏览，又能避免同名覆盖。图库记录与占问记录一并保存，使用户能够从星语图库、占问完成页和档案详情三个入口回到同一张图。

该方案的关键价值是：图片可被系统默认查看器打开、可另存到任意位置、可在数据库之外独立备份，同时仍保留与占问语境的关系。

### 5. 数据位置迁移与历史路径兼容

用户最终希望数据库、图片和备份都位于软件安装目录同级的 `data` 文件夹。这个要求看似只是修改一个路径，但涉及既有安装、旧数据库和已保存绝对图片路径的连续性。

v260825G 将数据根从旧的本地应用数据目录迁移至 `current_exe().parent()/data`。首次启动时，程序会在新数据根不存在数据库而旧数据库存在时复制旧资料；随后在 SQLite 中把历史图片路径的旧根前缀改写为新根前缀。由此避免了升级后数据库仍指向旧图片位置的问题。

这次迁移也体现了桌面产品的重要原则：**数据结构升级必须考虑旧用户，而不是只在干净环境中成立。**

### 6. Tauri 权限、asset 协议与本地图片显示

本项目最具代表性的系统难题之一，是“图片文件已经生成并能在磁盘找到，但应用里只显示破损图标”。它涉及多个独立环节：生图响应、文件归档、数据库路径、前端 `convertFileSrc`、Tauri `asset` 协议、CSP、路径 scope、WebView 解码以及 Windows 文件路径编码。

早期的“打开原图”还遭遇过前端 opener 插件的 ACL 拒绝。解决方式是将动作移到 Rust 后端：后端先 canonicalize 真实路径，确认其存在且位于 `data/images` 内，再调用系统默认图片查看器。这样既绕过了不必要的前端权限阻塞，也避免前端任意路径打开的安全风险。

v260826D 针对“文件存在但网页显示失败”又增加了双层保障：首先扩大 asset 协议对图片目录和月份子目录的匹配；若 asset URL 仍失败，则前端调用受限后端读取命令。后端再次验证路径仅位于图库目录，按照文件魔数识别类型，再将单一图片转为 data URL 回传界面。由此，图库、档案和占问完成页都能在正常 asset 读取失败时安全回退显示。

> 这一难点说明：本地文件“能写入”不等于 WebView “能读取”。桌面应用中的文件系统、协议权限与渲染层必须被作为一条完整链路一起设计。

### 7. 初始化功能的 IPC 参数解码问题

设置页的“初始化”需要支持多种选择：是否删除图片、是否删除 Profile、是否删除凭据，并要求最终文字确认。最初通过带布尔参数、嵌套对象和 JSON 字符串的 Tauri 命令传递选项时，在真实 Windows 环境连续出现 `expected a boolean`、`options` 映射失败和“初始化选项格式无效”等 IPC 参数解码问题。

最终没有继续在参数形状上反复试错，而是改变命令边界：前端先完成两次确认和“初始化”文字确认，再只根据用户选择调用四个**零参数命令**之一。四个命令分别映射到“保留全部资源”“删除图片”“删除 Profile”“删除图片和 Profile”四种固定后端行为。

| 旧思路 | 问题 | 最终方案 |
|---|---|---|
| 带多个布尔参数的命令 | 前端调用参数映射可能与 Rust 反序列化不一致 | 不传参数，使用固定零参数命令。 |
| 嵌套 options 对象 | 仍可能被框架按错误类型解析 | 前端只选择命令名。 |
| JSON 字符串 | 增加解析层，错误仍难定位 | 删除自定义 JSON 解析边界。 |

这是一次重要的工程经验：当跨语言 IPC 的参数映射反复不稳定时，**减少命令参数面**往往比增加序列化技巧更可靠。

### 8. 训练场从“让 AI 假装随机”到“本地真实随机”

训练场早期把“随机生成问题并随机掷出三颗骰子”完全交给 AI。用户发现训练中会出现重复骰面，这暴露了一个本质问题：语言模型可以生成看似随机的结果，但它不是可验证的随机源，也可能受到采样参数、服务端缓存或固定提示词的影响。

v260826C 对此进行了结构性修复。Rust 后端使用操作系统安全随机熵源，通过无偏索引从行星、星座、宫位各 12 个骰面中独立抽样。训练流程改为：**先在本地确定真实三骰，再把真实骰面交给 AI 生成相配的问题**。AI 不能替换骰面，也不再承担随机数职责。

项目也尊重真实随机的含义：不人为禁止连续重复完整三骰组合。重复虽然少见，但在真正随机的 1,728 种完整组合空间中本来就可能发生；通过“强制不重复”获得的只是更像随机的体验，而不再是独立随机抽样。

### 9. 训练题材控制、AI 评分与历史兼容

用户希望训练题不要总偏向职场，但又不希望默认限制题材。系统因此在偏好页增加可复选范围：默认全部不选，提示词不附加范围；用户勾选后，已选的关系、人际、家庭、职场、学习、财务、身心、创作、出行、个人选择等范围才会传入出题提示词；“其它”可填写不超过 15 字的自定义范围。

训练点评也从单纯文字反馈扩展为 AI 1–100 分评分。评分与点评一起保存，星语档案查询列表展示新记录的分数，而旧训练记录因没有该字段仍可正常显示“未评分”。SQLite 迁移通过新增 `ai_score` 默认列实现向后兼容，避免要求用户清库或重建档案。

这部分工作解决了“新功能上线不能牺牲旧资料”的长期维护问题。

### 10. 系统标签与用户标签的权限边界

“自动”“手动”“图片”承担的是系统事实：骰子是自动还是手动产生、是否已生成图片。它们不应被用户误删、改名或从记录中移除，否则档案语义会被破坏。

项目将标签区分为系统标签与用户自定义标签。系统标签仍显示在案例标题和过滤中，但不出现在可编辑标签池；后端也防止对这三个名称进行编辑、删除或从对应记录中移除。该设计既保留用户自由的彩色标记体系，又保证关键业务状态可信。

### 11. 可持续发布：严格相邻补丁、回滚与完整安装包

桌面应用交付不是“生成一个 exe”就结束。项目建立了按东八区日期的版本规则：`vyyMMdd + 字母序号`，同日 A–Z 后 AA、AB，日期变化后重新从 A 开始；默认使用严格相邻补丁，只有用户明确要求时才生成完整安装包。

每个补丁通过 NSIS 实现来源版本检查、主程序备份、覆盖、失败回滚与 `DisplayVersion` 更新；发布前执行前端构建、Rust 测试、Windows x64 交叉构建、NSIS 编译、7z 内容检查和 SHA-256 校验。这样可以避免把本应从 B 升级的补丁错误安装到 A 或 C，也给出现异常时提供了可恢复路径。

最终在开发阶段收束时，项目还提供了 v260826D 完整安装包和不含用户数据、密钥、构建缓存的可复建源码归档。

## 四、工程验证机制

《璇玑录》的验证并不只依赖一次“能否运行”。随着迭代，验证体系逐步扩展为：

| 验证层 | 方法 | 覆盖重点 |
|---|---|---|
| 前端构建 | `pnpm build` | TypeScript 类型、React 构建与资源打包。 |
| Rust 单元测试 | `cargo test` | SQLite 迁移、初始化选项、系统标签、随机骰面、图片路径校验、导出数据与评分字段。 |
| Windows 构建 | Tauri Windows x64 交叉构建 | 主程序是否能在目标架构产出。 |
| 安装包验证 | NSIS 编译与归档检查 | 补丁／完整安装包是否包含正确的主程序。 |
| 完整性验证 | SHA-256 校验 | 交付文件在构建与传递后是否保持一致。 |
| 真实环境反馈 | 用户 Windows 实机安装与操作 | 捕捉云端 Linux 环境无法模拟的 ACL、WebView、安装路径和默认查看器问题。 |

最终 v260826D 的回归测试覆盖 17 项 Rust 测试；更重要的是，整个项目持续将用户在真实 Windows 环境遇到的现象反馈到架构调整中，而非仅在云端构建成功后就视为完成。

## 五、最重要的开发经验

### 先定义数据与权限边界，再实现功能细节

SQLite 与图片文件如何分工、密钥在哪里保存、前端能否直接打开路径、导出包能否带 Profile，这些问题一旦迟到，后续改动成本很高。《璇玑录》的演进表明，本地软件的品质主要来自数据、权限与迁移边界的清晰，而不仅是页面数量。

### 将外部 AI 视为不稳定的能力，而不是系统真相

AI 可以生成解读、训练问题、评分和图像提示词，但不应决定本地随机骰面，不应保管用户密钥，也不应成为唯一档案载体。把“随机”“存储”“权限”收回本地，把“语言与创作”交给可替换模型，形成了更稳健的分工。

### 不要用复杂参数修补不稳定边界

初始化 IPC 的多轮修复证明，降低接口复杂度往往比添加更多 JSON、嵌套对象或兼容分支更有效。四个零参数命令虽然朴素，却使前端确认流程与后端危险操作之间的边界清晰、稳定且可测试。

### 发布机制是产品能力的一部分

版本编号、相邻补丁、来源版本检查、回滚、哈希和完整安装包不是“最后打包时再考虑”的工作，而是用户敢于长期保存档案、持续升级软件的基础。

## 六、结语

《璇玑录》最终完成的不只是一款拥有神秘视觉风格的占星骰子软件，也是一套围绕本地档案、可替换 AI、真实随机、隐私保护和可持续发布建立起来的个人工作台。

它把看似分散的需求——占问、训练、图库、标签、备份、导入导出、密钥、安装包、补丁——连接成了一条完整的用户路径：用户提出问题，掷下真实骰面，获得辅助解读，生成或保存图像，训练自己的理解，在未来回看当时的记录，并始终保有对模型与数据的掌控。

> 从 v260825A 到 v260826D，最有价值的成果不是某一个按钮或一次修复，而是把“能运行的原型”逐步打磨成“能够被长期使用、维护和信任的本地软件”。
